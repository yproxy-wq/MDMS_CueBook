# Session Recovery：調査と改善計画

調査日：2026-10-03。対象：v0.98-dev.39、ブランチcodex/uiux-audit-20261003。ユーザーの指定は「調査と改善計画まで」。アプリコード・保存データ・配備は変更しない。以下は未実装の提案であり、現行仕様ではない。

## 結論と根拠

正常な別タブの起動と異常終了を区別する生存判定がない。先行する本番E2Eでは、専用シナリオを開いたタブが稼働中でも、追加タブにSession Recoveryが表示された。今回はその観測と現行コードの対応を調査した。新たな本番操作や異常終了の実行は行っていない。

| 所見 | 根拠 | 判定 |
|---|---|---|
| 稼働中も未正常終了として扱う | useSessionRecovery.ts:35〜49で起動時に共通終了フラグを読み、その後falseを保存。生存中の別タブ確認はない | コード確認済み。既存E2Eの誤警告と整合 |
| バックアップと終了フラグが端末内で共通 | sessionRecoveryService.ts:9〜10の固定キー。タブ・アカウント・シナリオによるキー分離なし | コード確認済み |
| あるタブの終了が端末全体を正常終了にできる | useSessionRecovery.ts:103〜107のbeforeunloadが共通localStorageへtrueを書き、サービスはそれを優先 | コードから推測。他タブの異常終了を隠すケースは未再現 |
| 起動判定が読み込み完了と競合し得る | isReadyがfalseの間だけ非同期確認し、trueへの変化でactive=falseにする | コードから推測。遅いIndexedDBでは実際の異常終了を見逃す可能性。未再現 |

| 復元対象の照合がない | App.tsx:1719の復元はbackupData.stateを全体適用し、isEditorModeだけ現在パスへ合わせる | コード確認済み。別scenarioId・別アカウントへの誤復元は未再現 |
| 復元／破棄が共通バックアップを削除する | App.tsx:1732〜1736、サービスの固定キー削除 | コード確認済み。他タブの新しい保存との競合は未再現 |

重大度：正常な複数タブ起動の誤警告はP2。誤復元・候補の消失・異常終了の見逃しはデータ保護上のP1候補であり、再現試験を先行する。

## 推奨設計

終了フラグを消すだけの対処は採用しない。復元案内を必要とする異常終了が見えなくなるため。まず「所有タブが生存している」「正常終了した」「復元候補がある」「状態を確認できない」を区別する。

1. 起動判定は1回の処理として管理し、シナリオ読み込みのisReady変化で途中キャンセルしない。アンマウント・対象アカウント変更時は古い結果を適用しない。判定対象は認証とscenarioIdの解決後に確定する。
2. 候補に所有タブID、アカウント範囲、シナリオID、保存世代、終了状態を持たせる。新しい保存は範囲ごとのキーへ書き、既存の共通バックアップは移行が完了するまで残す。認証待ちを未ログイン範囲と誤認しない。
3. 所有タブの生存判定はWeb Locksが利用できる環境では、所有タブの保持するロックで確認する案を優先する。起動判定の排他用ロックは短く保持し、既存タブを待たせ続けない。実装可否と対象ブラウザは機能検出・実機試験で確認する。
4. 非対応環境ではBroadcastChannelの生存問い合わせを代替候補とする。返答がある場合だけ生存を確定し、無応答をそのまま死亡と扱わない。背景タブ・端末スリープを考慮し、確認不能時は異常終了を断定せず、バックアップを保持した任意の復元導線を出す。
5. 各タブは自身の終了状態だけを更新する。別タブを閉じても生存中の所有者や他の復元候補を正常終了にしない。共有のtrueフラグを新方式で継続利用しない。
6. 復元候補の選択中はその候補を保存・削除で上書きしない。新しいセッションの保存は別キーへ分離する。復元／破棄は選んだ所有者・保存世代だけに作用し、読み取り後に他タブが保存した新しい世代は削除しない。
7. 復元前にアカウントとシナリオを照合する。別シナリオの候補を現在の状態へ黙って適用せず、候補のタイトルと保存日時を示す。アカウントの確認不能・不一致で他者の内容を表示しない。旧データには所有者情報がないため、自動移行・自動適用を避けて扱いを明示する。

Web Locksが同一のストレージ範囲にあるタブ間の協調と所有者の終了後の引継ぎに利用できることは[W3CのWeb Locks仕様草案](https://www.w3.org/TR/web-locks/)に記載されている。このAPIだけではシナリオやアカウントの分離は行われないため、アプリ側で範囲を設計する。採用は未決定。

## 実装工程と受入条件

| 順序 | 作業 | 受入条件 |
|---|---|---|
| 1 | 現行不具合の再現テスト | 稼働中の追加タブ、終了フラグ競合、遅い起動判定、復元待ちの上書きをそれぞれ失敗として捉える |
| 2 | 起動判定と生存確認を分離 | 正常な追加タブで遮断モーダルなし。所有者不在の未正常終了では復元候補を保持。確認不能時も候補を失わない |
| 3 | 保存範囲・世代・旧データ移行 | 他シナリオ・他アカウント・他タブの保存を上書き／削除しない。旧共通候補を移行前に消さない |
| 4 | 復元導線と候補保護 | 復元前に対象確認。待機中に候補が変わらない。復元成功後だけ対象世代を完了扱いにする |
| 5 | 回帰とローカルE2E | 下記ケースに加え、タイマー基準時刻、音源設定、Sync Studio、シナリオ別進行の既存テスト成功 |
| 6 | 専用シナリオで本番相当確認→配備 | ユーザーの実装承認後に実施。通常シナリオでクラッシュや破棄を試さない |

起動判定・生存確認でアプリ全体を毎秒再描画させない。既存のバックアップ周期やTimer/AudioServiceの算出・再生は別責務として維持する。仕様変更後はSpec-SheetとSpec-Historyを更新する。

## 実装・受入検証（2026-10-03 / v0.98-dev.40）

調査提出後のユーザー「OK。実施」により、永続化コアの改善を実装した。上記の「未実装」「調査まで」は調査時点の記録であり、以後はこの節が実施状況を示す。

- 認証確定とシナリオ準備完了後の判定に変更し、早いisReady遷移による確認キャンセルを解消。アカウント／シナリオ変更・アンマウント後の結果と、復元保存待ちの古い操作結果は適用しない。
- 所有タブ別・アカウント別・シナリオ別のv2保存と、世代・時刻・状態構造の検証を追加。新しい保存は従来候補と別キー。保存完了はIDBリクエスト成功ではなくトランザクション完了を待つ。
- Web Locksで生存確認し、候補確認中は専用ロックで予約する。同時起動の別タブは待たされず、同じ候補を二重に表示しない。旧候補の自動移行がないため、全起動を直列化する共通ロックは導入しない。
- API非対応／問い合わせ失敗時はBroadcastChannelの肯定応答のみ利用。無応答は確認不能であり、強制モーダルにしない。pagehide/pageshowによる正常終了記録は自身の所有者だけを対象とし、BFCacheのpagehideは正常終了扱いにしない。
- 復元先保存が失敗した場合は画面と候補を保持。復元／破棄は選択したキー・世代をトランザクション内で照合する。新世代と旧固定キーは削除しない。「今は続ける」も候補を保持する。
- 旧固定キーは所有アカウントを確認できないためタイトルを自動開示せず、自分の保存として明示確認した場合だけ現シナリオと照合する。旧候補は復元しても元キーを保持する。新方式の正常終了／期限外レコードも今回の改修では自動削除せず保持する。
- 対象と日時を示す日本語モーダル、44px以上の操作、Escape、Tab循環、フォーカス復帰を追加。内蔵ガイドを実際の保存周期・復元範囲に合わせた。startTime/seconds算出、AudioService、Firestore同期エンジンは変更していない。
