# Biz音源一覧同期の検証記録

対象: v0.98-dev.37。実行順: 実装 → E2E 1回目 → リファクタリング → E2E 2回目 → Biz配備。

## E2E 1回目（リファクタリング前）

Chromeの独立した2タブで実際のSoundTab・SoundSettingsPanel・同期フックを操作した。Firestore通信だけはローカルのSSE／HTTPテスト用通信へ置換した。Firebase本番認可・R2実ファイルの保存／再生を検証したものではない。

- 空の2画面から、画面Aで音源追加・「E2E曲A」へ命名 → 画面Bに自動表示: 成功。
- 画面Bで「E2E曲B」へ改名 → 画面Aへ反映: 成功。
- 画面Bを再読み込み → 保存済み一覧を復元: 成功。
- 画面Bで音源削除 → 画面Aの一覧も空に更新: 成功。

## リファクタリング

純粋な差分処理をaudioLibrary.ts、接続中の保存状態・初回読込・再試行をAudioLibrarySession.tsへ分離。ReactフックはBizクレームの検証・購読寿命・音源一覧だけの状態反映に限定した。

## 自動回帰テスト

最終確認: 50ファイル・252テスト成功。型検査・Lint・Biz／Stableビルド成功。FirestoreルールはBizプロジェクトを対象にdry-runでコンパイル成功（公開は行っていない）。

- 2つの独立Reactルート: 既存曲の初回登録／空の別端末の読込、追加・編集・削除、保存の反射ループ防止、同時フィールド編集、アカウント／シナリオ分離、通常版の接続抑止。
- セッション境界: サーバー初回読込前の保存抑止、空の初期端末の登録抑止、通信失敗時の差分保持・再試行、再起動時の差分復元、退出時保存、遅延応答破棄、Blob/Data URL除外。
- Firestoreアダプター: キャッシュ由来・未確定スナップショット除外、metadata-only更新の購読、最新トランザクションへの差分統合、不正データによる上書き抑止。
- 同梱ガイド・2デモ: IndexedDB未保存状態でも指定IDから解決し、保存済み編集を優先する。

## E2E 2回目・配備

Chromeの画面操作がタイムアウトしたため、再開時にCodex内蔵ブラウザへ切り替え、独立した2タブで同じ編集UIを検証した。通信は1回目と同じローカルのテスト用通信で、本番Firebase認可・R2実ファイル再生の検証とは区別する。

- 画面Aで追加・命名 → 空の画面Bへ自動反映: 成功。
- 画面Bで曲名・SEからBGMへ変更 → 画面Aへ反映: 成功。
- 画面Aを再読み込み → 一覧・曲名・種別を復元: 成功。
- 画面Bで削除 → 画面Aへ反映: 成功。
- 新規追加後、削除を画面Aで確認して8秒以内に「元に戻す」 → 両画面へ復元: 成功。
- テスト用R2 URIを画面Bで入力 → 画面AのURL入力へ反映、再読込後も保持: 成功（実在R2ファイルの取得／再生は実施していない）。

2回目E2E完了後、Biz配備へ進む。

## 再現手順

`npm run test:e2e:audio` でテスト用サーバーを起動し、`http://127.0.0.1:3012/tests/audio-sync/` を2タブで開く。追加・命名・逆方向の編集・削除・取り消し・再読込を実行する。サーバー内テスト台帳はメモリだけに保持し、再起動でリセットされる。この画面と通信は本番エントリーポイントから参照されず、製品ビルドへ含まれない。

導入後の既存R2音源は、曲を登録した元ブラウザで新版を開いた際に初回登録される。別端末は同一アカウント・同一シナリオで受信する。端末専用ファイルはCloudflareに保存し直す必要がある。
